The Latest has been built into a multi-surface news aggregation product focused on live news, opinions, podcasts, videos, social signals, source trust context, and side-by-side perspective comparison. 1. ADMIN ACCESS FAIL-CLOSED FIX

- Fixed canManageAdminActions() to fail closed: an empty allowlist now denies admin access to everyone instead of granting it to everyone.
- Confirmed admin access here is entirely homegrown (netlify/functions/authStore.js: scrypt password hashing, HMAC-peppered session tokens in Netlify Blobs) -- there is no third-party identity provider or SSO involved. Admin status is purely "is this authenticated account's email in the ADMIN_EMAILS allowlist."
- Set ADMIN_EMAILS=24.chernandez@gmail.com locally (.env) and in Netlify (production, deploy-preview, branch-deploy contexts) via the Netlify CLI, with an inline TODO comment (in .env and .env.example) to swap to an Our National Conversation org/domain email once one exists.
- Updated scripts/verify-deploy-env.mjs's ADMIN_EMAILS guidance text to reflect the new fail-closed behavior.

2. AUTH RATE LIMITING
- netlify/functions/auth.js's register and login actions had no rate limiting at all, despite netlify/functions/rateLimit.js already being used elsewhere (searchAssist, sharedSummary, generatedContent, rss-aggregator).
- Added enforceRateLimit to register (5 requests/min per IP) and login (10 requests/min per IP+email combination), returning 429 with Retry-After when exceeded.

3. CONTENT-SECURITY-POLICY HARDENING
- netlify.toml previously shipped a CSP with only base-uri/frame-ancestors/object-src -- no script-src, style-src, img-src, font-src, or connect-src restriction at all, meaning script and connection sources were effectively unrestricted.
- Added explicit directives: script-src 'self' 'unsafe-inline', style-src 'self' 'unsafe-inline', img-src 'self' data: https:, font-src 'self' data:, connect-src 'self' https://www.reddit.com https://api.openai.com https://api.perplexity.ai, frame-src https://www.youtube.com, media-src 'self' https:.
- script-src and style-src keep 'unsafe-inline' deliberately: SeoManager.jsx injects per-route JSON-LD structured data as a dynamically created inline <script>, and the app renders React inline style={{...}} attributes throughout -- both are static-site constraints (no per-request server templating to hand out a CSP nonce), documented inline in netlify.toml.
- Verified the header live: ran `netlify dev`, confirmed the CSP header is actually served, then drove a headless Playwright browser across home, an article page, /videos (YouTube iframe), a /topic page (direct-from-browser Reddit fetch), and /dashboard. First pass caught one real violation (the JSON-LD inline script); after adding 'unsafe-inline' to script-src, zero CSP violations and zero console errors across all five routes. Confirmed with a homepage screenshot that rendering (including the live server-side Claude AI briefing) was unaffected.

4. LIGHTWEIGHT CLIENT ERROR REPORTING
- There was previously no production visibility into client-side errors -- ErrorBoundary.jsx only did console.error, which is invisible once deployed.
- Added netlify/functions/clientError.js: rate-limited (20/min/IP), truncates and logs incoming error reports via console.error (visible immediately in Netlify function logs) and aggregates them into Netlify Blobs (STORE_NAMES.clientErrors) keyed by day + message/path signature with a running count.
- Added src/services/errorReportingService.js as the client-side POST helper.
- Wired it into ErrorBoundary.jsx's componentDidCatch (React render errors) and into src/main.jsx via window 'error' and 'unhandledrejection' listeners (errors outside the React tree).
- Deliberately did not require signing up for a third-party service (Sentry/Datadog/etc.) -- this gives baseline visibility without a new external dependency or account.

HSTS AND ACCOUNT-RECOVERY HARDENING (08/19/2026)
A third same-day follow-up pass covering the two "worth doing before launch" items from the last review round: transport-security headers and a missing password-recovery flow.

1. STRICT-TRANSPORT-SECURITY HEADER
- Added `Strict-Transport-Security = "max-age=31536000; includeSubDomains"` to both header blocks in netlify.toml.
- Deliberately left off the `preload` directive -- submitting to the browser HSTS preload list is a separate, much harder-to-reverse commitment (it affects every subdomain indefinitely and takes a manual removal request to undo) that should be a deliberate later decision, not a side effect of this change.

2. PASSWORD-RESET ("FORGOT PASSWORD") FLOW
- The auth system had register/login/logout but no account-recovery path, meaning a user who forgot their password had no way back into an account with saved follows/dashboard data except abandoning it and re-registering.
- Backend: netlify/functions/authStore.js gained createPasswordResetToken, consumePasswordResetToken (single-use -- the record is deleted on lookup whether or not it's still valid, so a token can never be replayed), and updateUserPassword, all built on the same scrypt/HMAC-pepper primitives already used for sessions. Generalized the session-token-hashing function into a shared digestToken so reset tokens reuse the same SESSION_TOKEN_PEPPER-based hashing rather than introducing a second secret.
- netlify/functions/auth.js gained two new actions: request-password-reset (rate-limited 5/min per email+IP; always returns the same generic "if an account exists..." message and only actually sends an email when the account exists, so the endpoint can't be used to enumerate registered emails) and reset-password (rate-limited 10/min per IP; validates the token, updates the password, and immediately signs the user in with a fresh session so they don't have to log in again right after resetting).
- Added netlify/functions/emailService.js: a minimal Resend-backed email sender (plain fetch call, no new npm dependency). Until RESEND_API_KEY is set, it logs the email (including the reset link) to the function's console instead of throwing, so the whole flow is testable in local dev / netlify dev before any email provider is configured. Documented the RESEND_API_KEY / EMAIL_FROM setup in .env.example, SECRETS_SETUP.md, scripts/set-hosted-secrets.ps1, and scripts/verify-deploy-env.mjs (recommended, not required -- reset emails just get logged instead of sent until it's set).
- The reset link's origin is reconstructed from the incoming request's Host/X-Forwarded-Host/X-Forwarded-Proto headers (falling back to VITE_SITE_URL, then a hardcoded default) rather than depending on an env var that isn't set in every context -- this way the link is correct whether the request came in on a custom domain, the raw *.netlify.app URL, a deploy preview, or local dev.
- Frontend: added a "forgot" mode to the existing LoginModal (a "Forgot password?" link under the password field switches to an email-only form, submits via a new requestReset() on AuthContext, shows a green confirmation message reusing the existing form styling) and a new standalone /reset-password page (src/pages/ResetPasswordPage.jsx, wired into App.jsx) that reads the token from the URL query, collects and confirms a new password, and calls a new completeReset() on AuthContext which both resets the password and persists the returned session (auto-login after reset).
- Added netlify/functions/auth.test.js coverage for both new actions (9 new tests): sends-email-and-generic-message for existing accounts, generic-message-with-no-email for non-existent accounts (enumeration protection), rate limiting on both actions, successful reset + auto-login, and rejection of invalid/expired tokens and too-short passwords.
- End-to-end verified live against `netlify dev`: registered a real test account, requested a reset, confirmed the (unsent, logged) reset link appeared correctly in the function console with the right host and protocol, drove the actual /reset-password page in a headless browser through to its "Password Updated" success screen, then confirmed login with the new password worked. Separately drove the LoginModal's "Forgot password?" click-through end to end (open modal -> Forgot password -> submit email -> green confirmation message), zero console errors. Cleaned up the test account (and its follows record) from the live Netlify Blobs store afterward via `netlify blobs:delete` since this local testing ran against the real hosted Blobs credentials in .env.

3. DEV-ERGONOMICS FIX FOUND ALONG THE WAY
- Running `netlify dev` populates a local `.netlify/functions-serve/` build cache containing copies of everything in netlify/functions/, including the *.test.js files added in the last two rounds. Vitest's default test discovery picked those copies up too, silently doubling the netlify/functions test count (61 real tests briefly reported as 113) any time someone had run `netlify dev` before `npm test`. `.netlify/` was already gitignored so this never affected CI, but it was a real local footgun. Fixed by excluding `.netlify/**` in vite.config.js's test config.
